而要让AI听话、写规范代码，核心工具就是Superpowers。

1. 从零理解 Superpowers

1.1 理解Superpowers之前，先理解背景：Claude Code 是什么

Claude Code 是一个运行在终端里的 AI 编码助手。它的背后是一个大语言模型（Claude）。你在终端里用自然语言告诉它要做什么（比如「帮我写一个用户登录功能」），它就会帮你读代码、写代码、运行命令、修 bug。

你可以把 Claude Code 理解为一个「会写代码的聊天对象」——你发消息给它，它回复你，并且可以直接修改你的项目文件。

1.2 问题在哪：为什么需要 Superpowers

默认情况下，当你对 Claude Code 说「帮我加个购物车功能」，它可能会直接开始写代码。这就像一个程序员拿到需求后不做设计、不写测试、不做计划，直接动手敲代码——虽然速度快，但：

  • 没有先讨论设计方案，可能方向做错
  • 没有先写测试，写出来的代码可能有隐藏 bug
  • 没有拆分任务，复杂功能可能顾此失彼
  • 没有代码审查，质量无法保证
  • 没有编码规范，变量的命名规则，代码组织结构，代码风格等无法保证

Superpowers 就是为了解决这个问题。

1.3 Superpowers 到底是什么

一句话：Superpowers 是一组写给大模型看的「工作指南」。

具体来说，Superpowers 就是一堆 Markdown 文件（纯文本），每个文件描述一套详细的工作流程。比如：

  • 有一个文件写着：「当你要写代码时，必须先写一个会失败的测试，运行看到失败，再写代码让测试通过」（这就是 TDD 技能）
  • 有一个文件写着：「当你要实现新功能时，先提出 2-3 个设计方案，分析优缺点，让用户选择后再动手」（这就是 brainstorming 技能）
  • 有一个文件写着：「当你收到任何任务时，先检查是否有对应的技能流程，不要跳过流程直接做」（这就是 using-superpowers 引导技能）

这些文件被统称为 「技能」（skills）。

1.4 核心原理：为什么给模型一段文字它就会「听话」

这是最关键的一点，也是之前缺失的解释：

大语言模型会遵循它在对话中收到的指令。

这不是什么魔法。大模型在生成每一句回复时，都会参考它之前「看到过」的所有文字——包括系统指令、对话历史和额外注入的上下文。如果它的上下文中包含一段话说「在写代码之前必须先写测试」，模型就会在后续的回复中遵循这个要求。

Superpowers 的全部工作原理就是：在你和 Claude Code 对话开始之前，自动把那些「工作指南」文字塞进模型的上下文里。模型看到了这些指南，就会按照指南要求的方式工作——先设计再实现、先写测试再写代码、不跳过流程步骤。

这就是为什么我们说「模型具备了 Superpowers 的纪律和技能使用指引」——不是模型本身变了，而是它读到了一份详细的行为规范，并按照规范行事。

1.5 打个比方

想象你新入职一家公司，主管给你一份《开发规范手册》——所有功能先写设计文档、所有代码先写单元测试、遇到 bug 先做根因分析。你读完后就会按手册办事。

Superpowers 就是这份手册，Claude Code 就是那个新员工。 每次对话开始时，手册会自动递给 Claude Code。

1.6 一句话总结

概念 是什么
Claude Code 运行在终端里的 AI 编码助手（背后是大模型 Claude）
Superpowers 一组 Markdown 格式的「工作流指南」，自动注入给模型以规范其开发行为
技能（Skill） 每一份独立的工作流指南，比如 TDD 技能、头脑风暴技能等
注入（Inject） 在对话开始时把技能内容自动塞进模型的上下文，让模型按此行事

2.2 启动

安装完成后，Superpowers 通过两种方式生效：

方式一：自动启动（无需操作）

当你在 Claude Code 中新建会话、恢复会话、清空或压缩会话时，Superpowers 会自动启动。

Claude Code 是怎么发现 Superpowers 这份「手册」的？

这要从插件安装说起。当你执行 /plugin install superpowers 时，Claude Code 会把 Superpowers 的所有文件（技能文件、脚本等）下载到本地的插件目录。关键是，这些文件里包含了一个钩子配置文件（hooks/hooks.json），它相当于对 Claude Code 说：

「嘿，每当有新会话启动时，请执行我指定的这个脚本。」

Claude Code 的插件系统会自动读取每个已安装插件的钩子配置。所以从安装完成那一刻起，Claude Code 就「知道了」：每次会话开始时要执行 Superpowers 的脚本。

结果：你在新会话中发第一条消息时，模型已经知道自己应该遵循 Superpowers 的工作流程。你不需要手动做任何事情——整个发现和注入过程由 Claude Code 的插件系统自动完成。

方式二：按需调用具体技能

自动启动注入的是「总纲」（using-superpowers），告诉模型要先查技能再动手。大部分情况下，模型会按照总纲自动判断并加载合适的技能。

但你也可以主动指定某个技能。比如你想先做设计讨论再写代码：

  1. 在终端启动 Claude Code（输入 claude 进入对话界面）
  2. 在对话界面中输入 /brainstorming 帮我实现一个搜索功能

模型会读取该技能的完整内容，然后严格按步骤执行。

2.3 验证 Superpowers 已在工作

安装后如何确认它生效了？看以下迹象：

  1. 模型主动声明：会话开始后，模型的行为会体现出它已收到 Superpowers 指引（比如主动问你是否需要先做设计讨论）。
  2. 技能加载反馈：调用具体技能后，模型会说明自己正在使用哪个技能、将按什么步骤执行。
  3. 流程约束：当你试图跳过步骤（比如不做设计直接写代码），模型会提醒你先完成前置步骤。
  4. 结构化输出：模型的回复会变得更有结构——先分析、再方案、再确认、最后实现，而不是一上来就给代码。

3. 核心概念

3.1 技能（Skill）

在第 1 节中我们提到 Superpowers 本质是一组「工作指南」，每份指南叫一个技能。这里展开说明。

技能长什么样

每个技能就是一个 Markdown 文件（SKILL.md），存放在 skills/ 目录下。文件顶部有名称和描述，正文是详细的操作流程。例如 TDD 技能里会写清楚：先写失败测试 → 运行确认失败 → 写最少代码通过 → 运行确认通过 → 重构。

模型加载技能后，就像读到了一份操作手册，会按照手册里的步骤严格执行。

有哪些技能

技能 一句话说明 什么时候会用到
brainstorming 先讨论设计方案，再动手 你要实现新功能、做架构决策时
writing-plans 把大任务拆成详细的实施计划 任务复杂、需要分步执行时
test-driven-development 先写测试、再写代码 写任何新功能或修 bug 时
systematic-debugging 系统化定位 bug 根因 遇到难以复现或复杂的 bug 时
subagent-driven-development 并行分配子代理执行任务 计划拆分完成后，要批量实现时
writing-skills 创建新的技能文件 你想自定义自己的工作流时

两种技能类型

  • 固定型（如 TDD、调试）：步骤严格，不能跳过或简化。
  • 灵活型（如某些模式类技能）：可根据具体情况灵活调整。

个人定制

你可以在 ~/.claude/skills 目录放自己写的技能，它们会覆盖同名的系统技能。这样你可以根据团队习惯定制工作流。

3.2 引导技能 using-superpowers

在 2.2 节我们提到，每次会话开始时会自动注入一个「总纲（程序的开发手册）」——这个总纲就是 using-superpowers 技能。它的作用是告诉模型：

  1. 先查技能再动手：收到任何任务时，先判断是否有对应的技能流程，有就先加载。
  2. 不要找借口跳过：技能文件中内置了大量「防偷懒」机制——列出了模型可能用来跳过流程的各种借口（如「这太简单了不用走流程」「我先看看代码再说」），并逐一反驳。
  3. 流程类技能优先：当多个技能可能适用时，先加载决定「怎么做」的流程技能（如 brainstorming），再加载指导「做什么」的实现技能。

对你来说这意味着什么？ 你不需要盯着模型看它有没有偷懒。Claude Code通过hook方式加载了using-superpowers这个技能，给模型灌输了一套开发流程，一旦模型开始执行任务，就会按照这套流程来执行，类比给程序员一部开发手册，程序员要按开发手册要求进行开发。

3.3 三大组件总览

如果你想了解 Superpowers 在技术上由哪些部分组成：

组件 位置 作用
技能系统 skills/ 目录（在插件安装目录内） 存放所有技能文件（Markdown），定义各种工作流
钩子系统 hooks/ 目录（在插件安装目录内） 在会话开始时自动执行脚本，把 using-superpowers 注入上下文
插件基础设施 .claude-plugin/ Claude Code 插件定义，让你能通过市场安装和更新 Superpowers

这些目录在你通过 /plugin install 安装后会自动部署到正确位置。日常使用中你不需要关心它们——安装好插件后一切自动运行。

4. using-superpowers规定的强制执行的开发工作流

4.1 「强制执行」是怎么实现的

在理解具体流程之前，有必要先说清楚一个关键问题：Superpowers 说的「强制执行」到底是什么意思？它是怎么做到的？

答案是：这里的「强制」是通过文字指令实现的，不是通过代码级的硬阻断。

Superpowers 没有任何脚本会阻止模型写文件、没有 CI/CD 门禁会拦截提交、也没有代码会检测你是否跳过了某个步骤。它的「强制」完全依赖于以下三层文字手段：

手段 做法 示例
强指令标记 技能文件中用 <HARD-GATE>、<EXTREMELY-IMPORTANT> 等标记包裹关键规则 brainstorming 技能：「在用户批准设计方案之前，不得写任何代码」
反合理化表格 列出模型可能用来跳过步骤的各种借口，逐一反驳 TDD 技能列了 11 种常见借口（如「太简单不用测」「先写后测也一样」），并解释为什么每一种都站不住脚
红旗清单 列出偏离流程的行为特征，告诉模型一旦出现就要停下来从头开始 TDD 技能：「先写了代码再写测试？删掉代码，从头来过。」

为什么这种方式有效？

回顾 1.4 节的核心原理：大模型会遵循上下文中的指令。当模型读到措辞极其强硬、逻辑严密、并且把所有「逃跑路线」都堵死的指令时，它几乎不会偏离——这和你读到一份写得非常严格且理由充分的操作规范后，很难找到借口不遵守的道理是一样的。

局限性

诚实地说，这种「强制」有边界：

  • 如果用户明确要求模型跳过某个步骤（比如「别做设计了直接写代码」），模型通常会听从用户
  • 极少数情况下，模型可能在复杂场景中「遗忘」或「忽略」某些指令

但在正常使用中，这套指令体系的效果非常可靠。

4.2 完整流程总览

Superpowers 定义了以下开发流程序列。通过上述指令手段，模型会按顺序执行，不会主动跳过任何步骤：

步骤 技能 目的
1. 头脑风暴 brainstorming 将想法提炼为经过验证的设计
2. Git Worktree （模型自动执行） 创建隔离的开发分支
3. 编写计划 writing-plans 拆分为详细的实现任务
4. 子代理实现 subagent-driven-development 自动化实施 + 两阶段审查
5. TDD test-driven-development RED-GREEN-REFACTOR
6. 代码审查 （模型自动执行） 提交前的质量验证
7. 分支合并 （模型自动执行） 合并回主分支

4.3 头脑风暴（Brainstorming）

在任何创意工作之前必须使用，包括创建功能、构建组件、添加功能或修改行为。

流程：

  1. 探索项目上下文
  2. 提出 2-3 种方法及权衡分析
  3. 展示设计方案并获得用户批准
  4. 编写设计文档
  5. 转入实现阶段

4.4 测试驱动开发（TDD）

严格的红-绿-重构周期，核心原则：「如果你没有看到测试失败，你就不能确定它测试的是正确的内容。」

流程：

  1. RED — 编写失败的测试
  2. Verify RED — 运行并确认测试按预期失败
  3. GREEN — 编写最少量的代码使测试通过
  4. Verify GREEN — 运行并确认测试通过
  5. REFACTOR — 在测试通过的前提下重构代码
  6. 重复以上步骤

4.5 子代理驱动开发（Subagent-Driven Development）

什么是子代理？ Claude Code 可以启动独立的「子会话」来执行任务，每个子会话叫一个子代理（subagent）。子代理有自己独立的上下文，完成任务后把结果汇报给主会话。好处是：每个子代理都是「新鲜的」，不会被前面任务的上下文污染。

流程：

  1. 把实现计划中的每个独立任务分派给一个新的子代理
  2. 子代理完成后，进行两阶段审查：先检查是否符合规范，再检查代码质量
  3. 若审查发现问题，子代理修复后再次提交审查
  4. 全部任务完成后汇总到主会话

5. 优势与局限

适合用 Superpowers 的场景

  • 复杂软件项目，需要系统化的开发流程
  • 团队协作，希望所有人遵循相同的工作规范
  • 对代码质量要求高，需要内置 TDD 和审查流程
  • 任务可拆分、可并行，适合子代理批量实现

可能不太适合的场景

  • 非常简单的改动（如改一行配置），流程会显得过重
  • 紧急修复且没有时间走完整流程时
  • 对 Claude Code 平台没有经验的新用户（建议先熟悉 Claude Code 本身再引入 Superpowers）

总结

回顾全文的核心要点：

Superpowers 是什么？ 一组 Markdown 格式的「工作流指南」，通过 Claude Code 的插件系统自动注入给大模型，让模型在帮你写代码时遵循先设计、先测试、不跳步骤的开发规范。

它怎么工作？ 安装插件后，每次你开启 Claude Code 会话，插件的钩子脚本会自动把引导技能（using-superpowers）的内容塞进模型的上下文。模型读到这份「行为规范」后就会按规范办事——遇到具体任务时再加载对应的详细技能（如 TDD、头脑风暴等）。

「强制」是怎么实现的？ 不是代码级的硬阻断，而是通过措辞严格、逻辑严密、堵死各种借口的文字指令。大模型会遵循上下文中的指令，这是整个系统的底层原理。

你需要做的事：

  1. 安装 Claude Code
  2. 在 Claude Code 中执行 /plugin install superpowers@superpowers-marketplace
  3. 开始对话——Superpowers 自动生效
  4. 需要时用 /技能名 主动指定某个工作流

AI 编码助手的能力已经毋庸置疑——它能读代码、写代码、跑命令、修 bug。但能力强不等于做事靠谱。一个没有流程约束的 AI 助手，就像一个技术过硬却从不写设计文档、从不写测试的程序员：活儿干得快，但方向可能跑偏、质量无法保证、复杂任务顾此失彼。

Superpowers 解决的正是这个问题。它不改变模型的能力，而是给模型注入了一套经过验证的工作纪律——先讨论设计再动手、先写测试再写代码、大任务先拆计划再逐个实现、完成后必须经过审查。而实现这一切的方式出奇简单：几份写给模型看的 Markdown 文件，通过插件系统在每次对话开始时自动注入。

如果你希望 AI 不只是”能写代码”，而是”能靠谱地做项目”，Superpowers 值得一试。
